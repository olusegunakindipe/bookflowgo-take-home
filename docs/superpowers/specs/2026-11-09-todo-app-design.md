# ToDo App: Design Spec

- **Date:** 2026-11-09
- **Status:** Draft, awaiting review
- **Scope:** Full stack. A React frontend (`web/`) connected to an Express backend (`server/`).
- **Effort budget:** 2–4 hours in total, as the brief asks. Anything outside the brief is out of scope.

## 1. Intent and success criteria

A single user maintains a ToDo list. The deliverable shows how requirements were interpreted, broken down, designed, implemented with AI, and verified.

Success means all of the following:
- Every target behaviour in the brief works end to end in the browser against the real API:
  - The user can see their list.
  - Completed items are hidden by default, and the user can choose to show them.
  - The user can create, edit and delete a ToDo.
  - The user can mark a ToDo completed and mark it incomplete again.
- Invalid input is rejected at the right boundary, and the user gets clear feedback.
- The data stays consistent: ordinals are unique, timestamps are UTC, and clients cannot set server-owned fields.
- Automated tests cover the meaningful behaviour, the validation rules and the failure cases on both sides.
- Git history shows the plan committed first, then coherent slices of work, each reviewed by the developer before it was committed.

**Out of scope:** auth or multiple users, reordering UI or endpoints, pagination, priorities or tags, `createdAt`/`updatedAt`, an overdue indicator, dark mode, animations, and deployment.

## 2. Domain model

| Field | API type | Client-supplied? | Default | Rules |
|---|---|---|---|---|
| `id` | string (UUID v4) | No | Generated by the server (`crypto.randomUUID()`) | Opaque. A path id that is not a UUID gets `404`. Chosen because it is built in (no dependency), uses a secure random source, is created in our code before the insert, and does not tie the API to a DB sequence. Autoincrement would also be acceptable for one user. UUID v7's index locality does not matter at this scale. |
| `title` | string | **Required on create** | – | Trimmed. 1–200 characters after trimming. Whitespace only counts as empty. |
| `description` | string | Optional | `""` | Trimmed. At most 2000 characters. An empty string means none (never `null`). |
| `dueAt` | ISO 8601 string or `null` | Optional | `null` | Must be a valid date-time **with an offset** (`Z` or `±hh:mm`). Normalised to UTC with `toISOString()`. Past dates are allowed. |
| `ordinal` | integer | No | `max(ordinal) + 1`, or `1` for the first item | Assigned by the server inside the `INSERT` statement itself (a single atomic statement). `UNIQUE` in the DB. |
| `completed` | boolean | Optional on update | `false` | – |

### Decisions

- **Length limits:** the limits are safety caps against abuse or accidents, not targets for typical input. A limit that is too low rejects real input (such as a pasted URL), while a limit that is too high costs almost nothing. The cap is 200 for the title and 2000 for the description. The largest valid body (about 8.8 KB even if every character is a 4-byte emoji) stays under the 10 KB body cap. Both sides count UTF-16 code units (JS `.length`, Zod `.max()`, HTML `maxLength`), so the client and server always agree.
- **Ordinal:** new items are appended at the end with max + 1. Deletes leave gaps, which is harmless because only relative order matters. There are no gaps reserved for inserts, because the brief does not require reordering (YAGNI). A future reorder would need a transaction with a two-step shift, because SQLite checks `UNIQUE(ordinal)` row by row during an `UPDATE`. Gaps would avoid the shift.
- **Date and time:**
  - The server stores and returns UTC only.
  - The web app uses `<input type="datetime-local">`, converts the local value to an ISO string in UTC before sending, and shows dates in the browser's local timezone.
  - A value without an offset is rejected, because it is ambiguous.
  - Past due dates are allowed, so a user can record an item that is already overdue or edit one after its due date has passed.
- **Completed items:**
  - The list endpoint excludes completed items unless `includeCompleted=true` is passed. Filtering happens in SQL.
  - When completed items are shown, they keep their ordinal position and are rendered with a struck-through, muted title.
  - The toggle is held in UI state and is not persisted.

## 3. API contract

The base path is `/api`. Bodies are JSON.

| Method and path | Request | Success | Failures |
|---|---|---|---|
| `GET /api/todos` | Optional query `includeCompleted`: exactly `true` or `false` (default `false`) | `200` `Todo[]`, sorted by `ordinal ASC` | `400` |
| `GET /api/todos/:id` | – | `200` `Todo` | `404` |
| `POST /api/todos` | `{ title, description?, dueAt? }` | `201` `Todo` plus a `Location` header | `400`, `413`, `415` |
| `PATCH /api/todos/:id` | At least one of `{ title, description, dueAt, completed }`. `dueAt: null` clears the date. | `200` `Todo` | `400`, `404`, `413`, `415` |
| `DELETE /api/todos/:id` | – | `204` | `404` |

`PATCH` handles both edits and completing or uncompleting an item. Request schemas are **strict**: unknown keys, including `id` and `ordinal`, are rejected with `400`.

### Error shape (every error)

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid request body",
             "details": [{ "field": "title", "message": "Title is required" }] } }
```

`details` is present only for `VALIDATION_ERROR`.

| Situation | Status | `code` |
|---|---|---|
| Field rule failed, unknown key, empty PATCH, or bad query | 400 | `VALIDATION_ERROR` |
| Malformed JSON | 400 | `INVALID_JSON` |
| POST or PATCH without `application/json` | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| Body larger than 10 KB | 413 | `PAYLOAD_TOO_LARGE` |
| Unknown id, non-UUID id, or unknown route | 404 | `NOT_FOUND` |
| Unexpected error | 500 | `INTERNAL_ERROR` (generic message; details logged on the server only) |

## 4. Architecture

### Server (`server/`): Node 20, TypeScript, Express 5, better-sqlite3, Zod

```
src/
  app.ts                 createApp(repo): builds the Express app; does not listen (testable)
  index.ts               reads config, opens the DB, listens
  config.ts              HOST (default 127.0.0.1), PORT (default 3001), DB_PATH (default ./data/todos.db)
  db/database.ts         openDatabase(path) and an idempotent schema migration
  http/errors.ts         AppError subclasses and a single error-handling middleware
  todos/todo.schema.ts   Zod schemas: CreateTodo, UpdateTodo, ListQuery, IdParam
  todos/todo.repository.ts  TodoRepository interface and the SQLite implementation
  todos/todo.service.ts  domain rules: defaults, UTC normalisation, not-found
  todos/todo.routes.ts   HTTP to service mapping; validates input with the schemas
```

Table: `todos(id TEXT PK, title TEXT NOT NULL, description TEXT NOT NULL DEFAULT '', due_at TEXT NULL, ordinal INTEGER NOT NULL UNIQUE, completed INTEGER NOT NULL DEFAULT 0 CHECK (completed IN (0,1)))`.

An index `idx_todos_completed_ordinal ON todos(completed, ordinal)` matches the default list query (`WHERE completed = 0 ORDER BY ordinal`).

- **No explicit transactions, because every write is one atomic statement:**
  - `create` is `INSERT … VALUES (…, (SELECT COALESCE(MAX(ordinal), 0) + 1 FROM todos)) RETURNING *`, so reading the max and inserting cannot be separated.
  - `update` is a single `UPDATE … RETURNING`, and `delete` is a single `DELETE` whose `changes` count of 0 means `404`.
  - A transaction would only be needed for a multi-statement write, such as a future reorder.
- Each statement is prepared once.
- Rows are converted to the API's camelCase shape by an explicit mapper in the repository. Responses never contain raw DB rows.
- **Middleware order:** `helmet()`, then the JSON content-type check, then `express.json({ limit: '10kb' })`, then the routes, then the 404 handler, then the error handler.

### Web (`web/`): Vite, React, TypeScript, Tailwind v4

```
src/
  api/types.ts           Todo, CreateTodoInput, UpdateTodoInput, ApiError (copied from §3)
  api/todosApi.ts        fetch wrapper: parses the error shape and throws ApiError (also for network failures)
  hooks/useTodos.ts      useReducer state: items, includeCompleted, loading, error, plus the actions
  validation/todoForm.ts pure validateTodoForm(values) → field errors (same limits as the server)
  components/TodoList.tsx    list and empty state
  components/TodoItem.tsx    completion checkbox, title, description, local due date, edit and delete
  components/TodoForm.tsx    shared by create and edit; inline errors and character counters
  components/ErrorBanner.tsx dismissible banner for failed actions
  App.tsx                composes the pieces; "Show completed" toggle
```

- **Dev setup:** the Vite proxy forwards `/api` to `http://localhost:3001`, so requests are same-origin and the server needs no CORS configuration.
- **How updates are applied:**
  - Each create, update or delete waits for the server's response and then applies the returned entity to local state. There are no optimistic updates.
  - If a request fails, the user's input is kept. A field-level `400` is shown inline on the matching input, and any other failure is shown in the banner.
  - A completed item is removed from view when the toggle is off.
- **UI** (light polish only; the backend is the priority):
  - A centred page with a header ("Show completed" toggle) and the create form at the top.
  - Todos are cards in a **responsive grid**: `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`. That gives 3 columns on desktop and fewer on narrow screens. Cards read left to right, top to bottom, which is ordinal order.
  - Cards are equal height and long text wraps (`break-words`). A completed card has a struck-through, muted title.
  - Edit opens the form inline inside the card. Delete asks for confirmation with `window.confirm`.
  - Accessible labels, visible focus rings, and loading or disabled states on the buttons.
  - The title and description inputs have **no `maxLength`**, because it silently truncates pasted text and would make the over-length error unreachable. Instead, the description shows a live `n/2000` counter, and any over-length field gets an inline error on submit without sending a request.
  - **Consistency across browsers:**
    - Tailwind preflight normalises default styles.
    - The system font stack is used.
    - Checkboxes use `accent-color` so they look the same everywhere.
    - The native `datetime-local` picker popup is drawn differently by each browser, but its value and behaviour are the same (documented).
    - Supported browsers are those of Tailwind v4: Chrome 111+, Firefox 128+, Safari 16.4+.

### Validation placement (approach A: server-authoritative)

- The **server** is the authority. Every write is parsed by a strict Zod schema at the route boundary, and the database adds `NOT NULL`, `UNIQUE` and `CHECK` constraints as the last line of defence.
- The **web app** mirrors the user-facing rules for instant feedback: title required and at most 200 characters, description at most 2000 characters, and a valid due date. Invalid forms do not send a request.
- The duplication is small. Tests on both sides protect the limits from drifting apart. A shared schema package is the documented next step if the contract grows.

### Design principles applied

| Principle | Where |
|---|---|
| Single responsibility | Routes handle HTTP, the service holds the rules, the repository holds the SQL, and `errors.ts` maps failures. On the web side: `todosApi` does I/O, `useTodos` owns state, components render, and `validateTodoForm` holds the rules. |
| Open/closed | New error types are new `AppError` subclasses; the error middleware does not change. |
| Liskov substitution | The SQLite repository and any test double both satisfy `TodoRepository`. |
| Interface segregation | `TodoRepository` exposes only `list`, `findById`, `create`, `update` and `delete`. Component props are minimal. |
| Dependency inversion | The service depends on the `TodoRepository` interface. `createApp(repo)` takes its dependencies by constructor injection, with no DI framework. |
| DRY, YAGNI, fail fast | One `TodoForm` and one error shape; nothing outside the brief; validate at the boundary and reject unknown keys. |

## 5. Security, performance and scale (proportionate)

The server is audited against the OWASP API Security Top 10, scaled to the brief: one user, no auth, run locally.

| Concern | Measure |
|---|---|
| Injection | Parameterised prepared statements only. |
| Mass assignment and property exposure (API3) | Strict Zod schemas reject unknown keys, including `id` and `ordinal`. Responses are built by an explicit row mapper. |
| Unrestricted resource consumption (API4) | 10 KB body cap. No rate limiting: it is not needed for a single user on localhost, and it is documented as the next step if the API is ever exposed. |
| Security misconfiguration (API8) | `helmet()` default security headers (it also removes the `X-Powered-By` header). Binds to `127.0.0.1` by default because there is no auth. No CORS (same-origin through the Vite proxy). |
| Error leakage | Generic `500` bodies. Stack traces are logged on the server only. |
| XSS (web) | React escaping. No `dangerouslySetInnerHTML`. |
| Dependencies | `npm audit` is run as a verification step. |
| Not done (outside the brief, documented) | Auth and object-level authorisation (API1/API2), HTTPS, CSRF (no cookies or session exist). |

- **Performance:**
  - The composite index `(completed, ordinal)` serves the default list query, and the `UNIQUE` index on `ordinal` serves `includeCompleted=true`.
  - Completed items are filtered in SQL.
  - Statements are prepared once.
  - No compression or caching, because there is nothing to gain on localhost.
- **Scale:**
  - There is no pagination, because a single user's list is small. It is the first thing to add for large lists.
  - SQLite with one process is suitable for one user.
  - Going beyond one process would require a server-based database.
- **Storage limitations:**
  - Data lives in a local SQLite file, so it survives restarts.
  - Tests use `:memory:`.
  - There is no concurrency control between multiple tabs; the last write wins.

## 5a. Failure handling (non-client failures)

**Server:**
- **Unexpected error in a route or service:** the catch-all middleware logs the full error and stack on the server only, and returns `500 INTERNAL_ERROR` with a generic message. The process keeps serving.
- **DB error partway through a write:** every write is a single statement, which SQLite runs atomically. A failure therefore rolls back fully, so no partial row or duplicate ordinal is left behind.
- **DB open or migration failure at startup:** fail fast. Log the error and exit with a non-zero code instead of serving in a half-working state.
- **Crash-level errors:** there are no custom process handlers. Express 5 already sends rejected async handlers to the error middleware, and Node 20's default for any other unhandled rejection or exception is to log it and exit. In production a process manager would restart the process (documented).
- **Graceful shutdown:** on SIGINT or SIGTERM, `server.close()` stops new connections and then `db.close()` runs.

**Web:**
- **`5xx` on a write:** show the banner *"Something went wrong on the server. Your changes weren't saved. Please try again."* The form keeps the user's input and the list is unchanged, because there are no optimistic updates.
- **Network failure:** when `fetch` throws, show the separate banner *"Can't reach the server. Check it's running and try again."*
- **Timeout:** every request is aborted after 10 s with `AbortController`, and the abort is treated as a network failure, so buttons never stay disabled forever.
- **Initial load failure:** the list area shows an error with a **Retry** button, not an empty list.
- **`404` on update or delete:** show *"This todo no longer exists"* and reload the list, which brings the UI back in line after a delete in another tab.
- **No automatic retries:** retrying is manual only, because `POST` is not idempotent and a blind retry could create duplicates.

## 6. Testing and verification

**Server (Vitest):**
- **Unit tests:**
  - The schemas: trimming, length limits, `dueAt` with an offset accepted and without one rejected, unknown keys rejected, empty PATCH rejected, and `includeCompleted` parsing.
  - The service: ordinal is max + 1, UTC normalisation, and not-found handling.
- **API tests (Supertest with a `:memory:` DB):**
  - The success path of every endpoint.
  - Hidden by default, and `includeCompleted` returning everything.
  - `ordinal` ordering.
  - Every error row in §3.
  - A repository double that throws: the response is `500` with the generic body and no stack trace.
  - `helmet` security headers are present.

**Web (Vitest + React Testing Library + jsdom; the global `fetch` is stubbed with `vi.stubGlobal`, so every flow test also exercises `todosApi`'s error mapping and timeout):**
- **Unit tests:** `validateTodoForm`.
- **User-flow tests:**
  - Creating a todo shows it in the list.
  - An empty title or an over-length description shows inline errors and sends no request.
  - Completing a todo hides it, and the toggle shows it again.
  - Uncompleting, editing and deleting work.
  - A server `400` maps its field errors onto the inputs.
  - A `500` shows the server-error banner and keeps the user's input.
  - A network failure shows the "Can't reach the server" banner.
  - A failed initial load shows the error with Retry, and Retry succeeds.
  - A `404` on update shows "no longer exists" and reloads the list.

**Manual checks:** run `npm audit` in both packages. Run both apps and go through every target behaviour in the browser, then run the README's `curl` examples. The README separates checks that were run from checks that were only planned.

## 7. Workflow and review gates

1. Spec (this file) is approved, then committed.
2. The implementation plan in `docs/superpowers/plans/` is approved, then committed **before any feature code**. It serves as the AI-facing prompt.
3. For each task, TDD: write a failing test, make it pass, then commit to `main` and **stop**. The developer reviews the commit, and the next task starts only after their approval. Requested changes become separate follow-up commits, so the review is visible in history. History is never rewritten (no squash, amend or force-push).
4. When the approach changes, the plan is updated in the same commit as the change.
5. Final steps: full verification, then the README (setup, design, AI usage and corrections, what was verified, time spent, limitations).

## 8. Decision log (developer direction during brainstorming)

- Scope confirmed as full stack, using the folders `web/` and `server/`.
- SQLite chosen over in-memory storage.
- Validation approach A (server-authoritative, mirrored in the web app for UX) chosen over a shared schema package or server-only validation.
- Ordinal step changed from the proposed +1000 gaps to **max + 1** (YAGNI, because reordering is not required).
- Explicit requirement added that the frontend checks text lengths before submitting.
- SOLID and related principles are applied where they do real work, and are mapped in §4.
- ID strategy questioned. `crypto.randomUUID()` kept, with a stated rationale (§2).
- Length limits questioned. 200 / 2000 kept as safety caps, with a stated rationale (§2).
- Developer asked what happens on server failures such as a `500`. Explicit failure handling added for both sides (§5a), with tests.
- Developer asked for a standards check on the backend. Server audited against the OWASP API Top 10. Added: rate limiting (`429`), `helmet`, binding to `127.0.0.1`, an explicit response mapper, a `(completed, ordinal)` index, graceful shutdown, and `npm audit`. Transactions are scoped honestly: needed only for `create`.
- Developer asked for the todos to be shown as a 3-column grid that looks consistent across browsers, with light polish only because the backend is the priority (§4 UI).
- Developer asked to keep only what is easy to explain. Removed: the explicit `x-powered-by` disable (`helmet` covers it), the SQLite WAL and other pragmas (no contention with one user), and custom process crash handlers (Node 20's default behaviour already covers this).
- Developer reviewed the spec for anything outside the brief and chose to remove rate limiting (not needed for a single user on localhost). Kept: `helmet`, `GET /api/todos/:id`, the `(completed, ordinal)` index, graceful shutdown, the `Location` header and the description counter.
- Plan review: removed `maxLength` from the inputs (a counter and inline error instead), and web tests stub `fetch` itself rather than mocking the API module. Both approved by the developer.
- Workflow changed from approve-before-commit to commit-then-review on `main`. The brief asks for preserved history that shows corrections, and approve-before-commit would hide them. No feature branch is used, because the brief does not require one.
- `npm audit` during Task 1 flagged zod 3 (high severity, runtime) and vitest 3 (critical, dev-only). The developer chose to upgrade to zod 4.6.7 and vitest 4.1.12 before writing code. Validation rules are unchanged.
- Developer questioned whether transactions are needed. Answer: no. better-sqlite3 is synchronous and single-process, so the read-then-insert could not interleave, and the `SELECT` wrote nothing that would need rolling back. `create` became a single `INSERT … SELECT` statement, so every write is now one atomic statement and there are no explicit transactions.
